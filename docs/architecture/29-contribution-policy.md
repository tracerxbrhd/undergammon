# 29. Contribution Policy

## Status

Accepted for UNDERGAMMON.

## Repository model

UNDERGAMMON is a public proprietary project, not an open-source project.

The source may be viewed and studied publicly, but reuse of project code is not permitted unless the project owner grants permission.

## External contributions

Issues and pull requests from third parties are allowed.

The project owner retains full discretion over whether a proposal or pull request is reviewed, changed, merged, or rejected.

Before external code contributions are accepted, the repository should include a `CONTRIBUTING.md` file. GitHub surfaces contribution guidelines directly in the repository and pull-request flow, so this is the canonical place for contributor expectations.

## Contribution terms

`CONTRIBUTING.md` must clearly state that a person submitting code for inclusion in UNDERGAMMON must have the right to submit that material and must allow the project owner to use the accepted contribution as part of the proprietary UNDERGAMMON project.

The exact legal wording will be defined separately before public contributions are actively accepted. It must remain compatible with the proprietary licensing policy defined for UNDERGAMMON.

## Third-party material

Contributors must not submit code, assets, fonts, audio, data, or other material that they do not have the right to contribute.

New dependencies must be reviewed together with their licenses. A dependency that conflicts with proprietary distribution must not be merged without explicit review.

## Repository community files

Before active public contribution, add:

- `LICENSE` with the proprietary / All Rights Reserved policy;
- `CONTRIBUTING.md`;
- `SECURITY.md`;
- pull request template;
- bug and feature-request issue templates.

The README should state clearly that the repository is public but the code is not offered under an open-source license.

## Pull request expectations

Pull requests should be small and reviewable and normally include:

- purpose and scope;
- linked issue where appropriate;
- tests for behavioral changes;
- verification notes;
- disclosure of new dependencies.

Large architectural changes should normally be discussed before implementation.

## Maintainer authority

Architecture, product direction, licensing, releases, and acceptance of contributions remain under the project owner's control.
